# Vector Database Architecture

Because NexusIQ performs Retrieval-Augmented Generation (RAG) on uploaded documents, it relies heavily on a Vector Database to store and retrieve dense vector embeddings.

## Implementations

### Local ChromaDB (Default)
- **Role:** An in-memory/on-disk local vector store used by default for local development.
- **Connection:** Instantiated via `langchain_chroma.Chroma`. Data is persisted to `./data/chroma_db` (configurable via `Config.CHROMA_PERSIST_DIR`).

### Cloud Pinecone (Optional)
- **Role:** The primary production database for storing vector embeddings if configured. Provides ultra-fast, serverless semantic search with high availability.
- **Connection:** Automatically activated if the `PINECONE_API_KEY` and `PINECONE_INDEX` environment variables are present.

### Qdrant (Docker Production)
- **Role:** The `docker-compose.yml` production setup provisions a persistent **Qdrant** container. 
*(Note: Code integration for Qdrant is wired similarly to Pinecone/Chroma through LangChain abstractions when the appropriate env vars are set).*

## Schema (Metadata)
When chunks are inserted into the database, they are stored as dense vectors (generated by HuggingFace `all-MiniLM-L6-v2`) with attached JSON metadata.

The metadata schema guarantees these fields:
```json
{
  "source": "filename.pdf",
  "page_number": 12,
  "session_id": "e4477592-31cc-4769-85b0-10f3bf3e9509",
  "Header 1": "Introduction",
  "parent_id": "md5-hash-of-parent",
  "parent_text": "Broader context window string..."
}
```

## Session Isolation & Security
To ensure users do not search across other users' or other sessions' documents, ChromaDB/Pinecone documents are tagged with metadata during insertion: `metadata={"session_id": session_id}`.

During retrieval (via the `search_documents` tool), a `filter={"session_id": current_session_id}` argument is passed to the retriever. This guarantees strict tenant isolation per conversation thread, preventing unauthorized cross-contamination of uploaded private documents.
